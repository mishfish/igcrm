# Telegram-бот як інтерфейс керування igcrm — дизайн

Дата: 2026-10-28

## Навіщо

Зараз керування відбувається через Directus (веб-адмінка): перевірка
карток контактів, які LLM позначив `needs_review = true`, і створення/
скасування ТТН Нової Пошти через ручний Flow. Щоб це робити, треба
відкрити ноутбук/браузер і зайти в Directus. Мета — винести найчастіші
дії в Telegram, щоб їх можна було робити з телефону в два тапи, і щоб
бот сам штовхав сповіщення з кнопками дії замість того, щоб людина
ходила в Directus перевіряти, чи щось з'явилось.

Користувачі: власник + кілька співробітників (усі — довірені люди,
відомі Telegram user id). Авторизація на старті — whitelist по
Telegram user id (без PIN/OTP, без ролей — свідомо спрощено, див. non-goals).

## Поточний стан (на чому будуємо)

- Один Go-бінарник `igcrm` (`cmd/igcrm/main.go`), без веб-фреймворку,
  `net/http` + `ServeMux`. Фонові задачі — тікер-голдовіни в тому ж
  процесі (`internal/extract.Worker`, `internal/jobs.TokenRefresher`,
  `internal/jobs.ProfileFetcher`), Postgres використовується як черга
  (`ClaimDue`/`Reschedule`), жодного message broker немає.
- Telegram зараз — лише одностороннє сповіщення: `internal/notify/telegram.go`,
  `Notifier.Alert(ctx, text)` — голий `POST /sendMessage` на один
  `TG_CHAT_ID`. Нема вхідних updates, нема бібліотеки бот-API, нема
  команд.
- LLM-флоу: `internal/extract/extract.go` рахує diff і викликає
  `Store.ApplyExtraction` (`internal/store/store.go`), який пише нові
  поля в `contacts` і ставить `needs_review = true` + лог у таблицю
  `extractions`. "Підтвердження" зараз = людина відкриває Directus,
  дивиться збережений фільтр `needs_review = true`, оком перевіряє
  картку і сама знає, що зняти прапорець (реального API
  confirm/reject немає).
- ТТН: `internal/shipping/handler.go` — `POST/DELETE /orders/{id}/ttn`,
  викликає `shipping.Service.CreateTTN`/`DeleteTTN`. Ендпоінт **без
  жодної автентифікації**, бо не проброшений у Caddy — його смикає
  тільки Directus Manual Flow з тієї ж docker-мережі.
- Авторизації/ролей у самому Go-сервісі нема взагалі. Directus має
  власний RBAC, але в проєкті не налаштований (один admin-акаунт).
- `SECURITY_HARDENING_PLAN.md` (ще не виконаний) уже фіксує, що
  Directus зараз висить у відкритий інтернет без basic auth/IP-фільтра
  і без 2FA — критична знахідка з аудиту 2026-10-24, не пов'язана з
  ботом напряму, але того ж класу ризику (вхід у систему керування
  без додаткового шару захисту).

## Цілі

1. Push-сповіщення в Telegram з inline-кнопками для двох головних дій:
   - підтвердити/переглянути картку контакту, яку LLM позначив
     `needs_review`;
   - створити або скасувати ТТН Нової Пошти для замовлення.
2. Pull-команди в боті, щоб не чекати push (`/review`, `/orders` і т.п.).
3. Авторизація: тільки users з whitelist можуть щось бачити/робити;
   решта — тиша (бот не підтверджує і не спростовує, що він живий, для
   чужого user id).
4. Аудит-лог усіх дій, зроблених через бота (хто/коли/що) — той самий
   принцип, що вже є для LLM (`extractions`).
5. Directus залишається "повною" адмінкою для рідких/складних дій
   (детальне редагування полів, перегляд повної історії, зміна
   товарів/цін вручну) — бот не замінює Directus, а знімає 80% рутинних
   дій, які інакше вимагали б відкрити ноутбук.

## Не-цілі (свідомо не робимо зараз)

- Повна заміна Directus. Вільне редагування будь-якого поля будь-якої
  таблиці через бот — це по суті переписати Directus UI в Telegram;
  не варто.
- Рольова модель (хто що може) — усі з whitelist мають однакові права.
  Якщо пізніше знадобиться розрізняти "власник" / "пакує посилки" —
  окрема фаза.
- PIN/OTP при старті сесії — відкладено (користувач свідомо обрав
  базовий whitelist на старт).
- Webhook-режим бота (вхідний HTTPS ендпоінт через Caddy) — обрано
  long polling, див. "Рішення" нижче.

## Анти-цілі (що б означало провал, навіть якщо технічно працює)

- Хтось поза whitelist може створити/скасувати ТТН або прочитати дані
  клієнтів через бота.
- Випадковий тап кнопки списує гроші (створює реальну ТТН у Новій
  Пошті) без явного другого підтвердження.
- Бот стає новою публічною поверхнею атаки на той самий сервер, який
  і так ще не захищений по `SECURITY_HARDENING_PLAN.md`.
- Дії через бота не видно потім "хто це зробив" — втрачається аудит,
  який зараз є для LLM-змін.

## Архітектурні рішення (мій вибір, з обґрунтуванням)

**Бот живе в тому ж Go-бінарнику `igcrm`**, новий пакет `internal/tgbot`,
стартується як ще одна гораутина в `serve()`, поруч із
`extract.Worker`/`jobs.TokenRefresher`. Не окремий сервіс/контейнер.

Чому: проєкт і так уникає зайвих сервісів (черги нема, усе в одному
бінарнику), бот потребує прямого доступу до `store.Store` і
`shipping.Service` — у процесі це прямий Go-виклики функцій, без HTTP-
хопа і без нового внутрішнього ендпоінта, який довелось би ще й
захищати окремо.

**Long polling, не webhook.** Бот сам стукає в Telegram
(`getUpdates`), а не Telegram стукає в нас. Чому: це означає **нуль
нових публічних ендпоінтів** — не треба додавати в Caddy ще один шлях,
вигадувати для нього secret-перевірку і думати про нього в контексті
вже відкритого питання з публічним Directus. Для кількох користувачів
і некритичної до секунд латентності (підтвердження картки, створення
ТТН) polling — абсолютно нормальний вибір, і він узгоджується з тим,
як решта сервісу вже працює (тікер-polling замість вебхуків, де тільки
можливо).

**Авторизація — whitelist по Telegram user id**, нова env-змінна
`TG_ALLOWED_USER_IDS` (comma-separated int64), по аналогії з тим, як
уже є `TG_CHAT_ID`. Перевірка на кожен update (message і callback_query)
до будь-якої обробки; якщо user id не в списку — update просто
ігнорується (без відповіді), щоб не підказувати стороннім, що бот живий
і що він щось перевіряє.

**Дані:** бот ходить напряму в `store.Store` (ті самі SQL-запити, що і
Directus читає через Postgres) — не через Directus REST API. Це
уникає залежності бота від Directus (Directus можна перезапускати/
оновлювати, не зачепивши бота) і не вимагає окремого service-токена
Directus.

**Push — кожному користувачу окремо, не в один груповий чат.**
`TG_ALLOWED_USER_IDS` — whitelist, але щоб кожен зі списку отримував
сповіщення з кнопками у своєму приватному чаті, бот зберігає мапу
`tg_user_id → chat_id`, заповнюючи її при першому `/start` від
користувача з whitelist ("реєстрація" в один крок, без паролів). Якщо
хтось зі списку ще не написав боту `/start` — він просто не отримує
push, доки не напише; `Notifier.Alert` (існуючий одноразовий алерт на
`TG_CHAT_ID`) лишається як є для системних сповіщень (збій токена,
backup) — це окремий канал, не плутаємо з push по діях.

**Offset `getUpdates` переживає рестарт процесу.** Бінарник
рестартується при деплої — якщо не зберігати `update_id`, при старті
можуть повторно прийти update'и, що летіли під час рестарту (включно з
натиснутою кнопкою "Підтвердити ТТН"). Рішення: зберігати останній
опрацьований `update_id` в Postgres (один рядок у маленькій
key-value-таблиці чи колонка в конфігу), а не тільки в пам'яті.
Додатковий запобіжник на рівні даних уже є "безкоштовно": `CreateTTN`
пише `UPDATE orders SET ttn=..., status='shipped' WHERE id=$1 AND ttn
IS NULL` — повторний виклик на те саме замовлення є no-op, а не
другою ТТН, тож навіть дубльований update не спише гроші вдруге.

**Стан багатокрокових діалогів (наприклад, "введіть вагу") —
in-memory, per-user, з TTL.** Проста мапа `tg_user_id → pending action`
(яка дія, для якого order_id, з яким кроком) з таймаутом ~5 хв і
кнопкою/командою "Скасувати". Якщо процес рестартнувся посеред діалогу
— діалог просто зникає, користувач починає дію заново (нічого
критичного не підвисає, бо сама дія ще не виконана до фінального
"Підтвердити").

## Функціонал бота

### MVP (фаза 1)

**Push:**
- Коли `extract.Worker` ставить `needs_review = true` — бот одразу шле
  повідомлення з карткою (ім'я, телефон, місто, відділення, розміри,
  що хотів купити) і diff "що змінилось" (з `extractions`), плюс кнопки
  `✅ Підтвердити` / `🔗 Відкрити в Directus`.
- Коли створюється замовлення (вже є алерт — просто додати кнопки
  `📦 Створити ТТН` / `🔗 Відкрити в Directus` до того ж повідомлення).

**Pull:**
- `/review` — список контактів з `needs_review = true` (якщо багато —
  по одному з навігацією "далі").
- `/orders` — список замовлень у статусі `new`/`awaiting_payment` без
  ТТН, з кнопкою створити ТТН на кожному.

**Дії:**
- Підтвердити картку → `needs_review = false` у `contacts`, лог дії.
- Створити ТТН → бот питає вагу (і опційно оголошену вартість) у
  відповідь текстом → показує підсумок → кнопка `Підтвердити створення`
  → викликає `shipping.Service.CreateTTN` напряму → шле номер ТТН.
- Скасувати ТТН → підтвердження → `shipping.Service.DeleteTTN`.
- Позначити замовлення `paid`/`delivered`/`returned`/`cancelled` —
  кнопками зі списку замовлення (прямий `UPDATE orders.status`).
  **`shipped` сюди не входить** — цей статус уже ставить сам
  `CreateTTN` при успішному створенні ТТН (`store.go`: `UPDATE orders
  SET ttn=..., status='shipped' WHERE id=$1 AND ttn IS NULL`); ручна
  кнопка "shipped" дублювала б цю логіку і могла створити стан
  "shipped без ttn" — не додаємо її.

Редагування окремих полів картки (ім'я, телефон і т.д.) **в MVP не
входить** — якщо щось не так, людина тапає "Відкрити в Directus" і
править там. Додати це в боті пізніше, якщо виявиться, що без цього
незручно.

### Фаза 2 (опційно, за потреби)

- Швидке редагування полів картки прямо в чаті (`/edit <contact_id> phone +380...`).
- Перегляд останніх N повідомлень переписки з контактом.
- Ручне створення нового замовлення з бота (не тільки авто з LLM).
- Ролі/права, якщо з'явиться потреба розділити, хто що може.
- 2FA/PIN при старті сесії, якщо з'явиться занепокоєння про compromised
  телефон.

## Безпека

1. **Whitelist по user id**, перевірка на кожен update (вище).
   Невідомий user — тиша, нуль відповіді.
2. **Long polling замість webhook** — нуль нових публічних HTTP-
   ендпоінтів, нуль нового роутингу в Caddy.
3. **Токен бота** — так само, як зараз `TG_BOT_TOKEN`: тільки в `.env`
   (`600 root:root`), не в коді, не в логах.
4. **Двокрокове підтвердження для дій, що коштують грошей/незворотні**:
   створення ТТН і зміна статусу замовлення — спочатку показати деталі
   (вага/сума/новий статус), і тільки друга кнопка `Підтвердити`
   виконує дію. Після виконання кнопки на повідомленні деактивуються
   (edit message, прибрати reply_markup), щоб не було подвійного тапу/
   double-submit.
5. **Аудит-лог**: кожна дія через бота (хто — Telegram user id,
   коли, що саме) пишеться в нову таблицю `bot_actions` (або просто
   structured `slog` з `action`, `tg_user_id`, `order_id`/`contact_id`)
   — той самий принцип, що вже є для LLM-змін через `extractions`.
6. **Rate limit per user** (просто, in-memory) — захист від зациклення/
   абʼюзу, якщо токен колись протече.
7. **Валідація callback_data**: кнопки несуть лише внутрішні числові
   id (order_id/contact_id) + назву дії — tamper-ризик низький, бо
   захист — саме whitelist (чужий user id взагалі нічого не отримає у
   відповідь), а не секретність callback_data.
8. **Directus лишається відкритим ризиком, незалежно від бота** — бот
   не закриває пункт 1 з `SECURITY_HARDENING_PLAN.md` (публічний доступ
   до Directus без basic auth/IP-фільтра/2FA). Це окрема, вже
   задокументована робота; варто зробити її паралельно чи раніше, бо
   інакше "головний вхід" лишається незамкненим, навіть коли рутинні
   дії переїдуть у бота.

## План реалізації (фази)

1. **Інфраструктура бота**: `internal/tgbot` — long-polling клієнт
   Telegram Bot API (getUpdates/sendMessage/editMessageText/
   answerCallbackQuery), запуск гораутиною в `serve()`, конфіг
   `TG_ALLOWED_USER_IDS`.
2. **Авторизація + аудит-лог**: мідлвар на update, таблиця/лог дій.
3. **Pull-команди**: `/review`, `/orders` + рендер картки/списку.
4. **Дія "підтвердити картку"**.
5. **Дія "створити/скасувати ТТН"** (з двокроковим підтвердженням).
6. **Дія "змінити статус замовлення"**.
7. **Push-сповіщення**: гачок у `extract.Worker` (після
   `ApplyExtraction`) і в місці створення авто-замовлення
   (`extract.Worker.Process`/`CreateOrderIfNone`) — замінити/розширити
   існуючий `Notifier.Alert` повідомленнями з кнопками.
8. Ручне тестування на staging/невеликій групі користувачів перед тим,
   як вимикати звичку ходити в Directus.

## Відкрито для builder'а (можна вирішити самостійно під час реалізації)

- Конкретна бібліотека для Telegram Bot API в Go (чи писати тонкий
  клієнт самостійно за зразком `internal/notify/telegram.go`, чи взяти
  готову) — нема явної залежності в `go.mod`, обидва варіанти ок.
- Формат рендеру картки/diff у повідомленні (Markdown vs HTML
  розмітка Telegram).
- Структура таблиці `bot_actions` vs просто лог — на розсуд, головне
  щоб "хто/коли/що" можна було відновити.
